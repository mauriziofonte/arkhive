# ArkHive 2.1: plan

Release 2.1 raises the bar on how ArkHive behaves as a system service. It builds on 2.0 (`docs/2.0-RESTIC-SPEC.md`, which stays the reference for everything this plan does not change) and keeps every 2.0 gate: PHPUnit coverage >= 90%, Infection MSI >= 80%, PHPStan level 8, PSR-12, e2e and distro matrix green.

Goals, as asked by the maintainer:

1. interoperability with systemd and its tools (`systemctl`, `journalctl`, timers);
2. logging through the journal (and syslog where there is no systemd);
3. robustness and resilience on errors;
4. exit codes following the open-source convention (`sysexits.h`);
5. SOLID / Domain-Driven Design restructuring of the code;
6. compatibility with the restic versions shipped by the supported distributions, not only the latest.

Each step below lands as one or more conventional commits, each with unit tests, static analysis and coding standard green; steps that change runtime behaviour also extend the e2e or compatibility suites.

## 1. Exit codes (`sysexits.h`)

2.0 used 0/1/2/3/4/10/130/143. 2.1 keeps the codes with a well-known meaning and moves every failure class onto `sysexits.h`, which systemd understands by name (`systemctl status` shows `status=75/TEMPFAIL`).

| Code | Name | When |
|---|---|---|
| 0 | `EX_OK` | success |
| 1 | failure | unclassified runtime failure, a confirmation the operator declined, `status --max-age` exceeded, `doctor` failed check |
| 3 | warnings | completed with warnings: snapshot created but some files unreadable, notification failed (same meaning as restic's 3) |
| 10 | update available | `self-update --check` only |
| 64 | `EX_USAGE` | bad option or argument, required answer missing in unattended mode, `--in-place` without `--force`, major self-update without `--allow-major` |
| 65 | `EX_DATAERR` | data verified and found wrong: `restic check` errors, drill mismatch, corrupt dump, legacy archive or download |
| 66 | `EX_NOINPUT` | an input does not exist: config file, password file, snapshot, path inside a snapshot, legacy archive, release |
| 69 | `EX_UNAVAILABLE` | a service or dependency is unavailable: repository unreachable or missing, restic or a dump binary missing or too old, database server down, PHP too old |
| 70 | `EX_SOFTWARE` | internal error: unexpected exception, restic output ArkHive cannot parse |
| 71 | `EX_OSERR` | a process cannot be started |
| 73 | `EX_CANTCREAT` | refused output: restore target not empty, not enough space, existing database for `--import-as`, unwritable log file |
| 74 | `EX_IOERR` | a filesystem is full while writing (repository, dump staging, extraction) |
| 75 | `EX_TEMPFAIL` | temporary: repository locked by another client, ArkHive lock held, timeout, GitHub API rate limit. Retrying later may succeed |
| 76 | `EX_PROTOCOL` | the releases API answered something that is not a valid release |
| 77 | `EX_NOPERM` | wrong repository or archive password, permission denied, password file readable by others |
| 78 | `EX_CONFIG` | configuration error: invalid value, removed 1.x key, missing required key |
| 130 / 143 | signals | interrupted by SIGINT / SIGTERM, cleanup done and lock released |

Mapping rules: one exception type per class (`UsageException` 64, `ConfigException` 78, `RefusedException` 73, `TemporaryException` 75, ...); restic failures are classified by `ResticErrors` (step 3) into these classes; `ExitCode` documents the table and a test asserts every code at least once (2.0 gate kept). The table goes in README.

Compatibility: 2.0 was only released as `2.0.0-rc.1`, so the change goes in before 2.0 is widely deployed; CHANGELOG lists it under "Changed" with the old-to-new mapping (2 becomes 64 or 78, 4 becomes 73 or 64).

## 2. Domain-Driven layout (SOLID)

The 2.0 code is organised by technical area under `app/Services`. 2.1 moves it to three layers, one namespace each, without changing behaviour (tests stay green at every commit):

- `app/Domain/<Context>`: pure models and rules, no I/O. Contexts: `Backup` (backup plan, summary, outcome), `Restore` (restore plan, target policy, selection), `Retention` (policy), `Repository` (snapshot, node, lock, repository stats, restic version and capabilities), `Database` (dump targets), `Configuration` (typed config, removed keys, exclusions), `Execution` (execution context, exit status).
- `app/Application/<UseCase>`: one service per use case (`RunBackup`, `RestoreSnapshot`, `MaintainRepository`, `RunDrill`, `Diagnose`, `InitRepository`, `SelfUpdate`, ...), orchestrating domain objects through ports (interfaces): `SnapshotStore` (the repository), `ProcessRunner`, `Notifier`, `LogSink`, `ServiceManager` (systemd notify), `RunStateStore`, `Clock`.
- `app/Infrastructure/<Technology>`: adapters: `Restic` (CLI client implementing `SnapshotStore`), `Process`, `Mail`, `Systemd` (notify, journal), `Syslog`, `Http`, `Filesystem`, `Dump` (mysqldump / pg_dump).

Commands in `app/Commands` stay thin: parse input, call one application service, map its outcome to output and exit code. They are the composition root together with `app/Providers`, so they may name adapters.

Enforcement: an architecture test (`tests/Architecture`) fails when `Domain` uses anything outside `Domain` and the shared kernel (`Exceptions`, `ExitCode`) or calls a PHP function with side effects, when `Application` uses `Infrastructure` or `Commands`, when `Infrastructure` uses `Commands`, or when `Application\Port` holds a class that is not marked as a port value.

As done: the move was one mechanical commit (a per-context split would have left the namespaces half moved between green commits). The application services keep their 2.0 names (`BackupRunner`, `RestoreRunner`, `MaintainRunner`, `DrillRunner`, `Doctor`, `SelfUpdater`) rather than being renamed to verbs: the rename would touch every test for no behavioural gain. Ports in place: `SnapshotStore` and `SnapshotStoreFactory` (restic), `ProcessRunner`, `Notifier`, `LogSink`, `HttpClient`, `Terminal`, `Prompter`, plus the domain `Clock`; `ServiceManager` and `RunStateStore` arrive with steps 4 and 5. Parsing restic's JSON moved out of the domain models into `Infrastructure\Restic\ResticOutput`, and building restic's backup and restore arguments moved into the adapter, which is where version-dependent arguments (step 3) live.

## 3. restic compatibility

Supported range: from the restic of Debian 11 to the current release.

| Distribution | restic |
|---|---|
| Debian 11 | 0.11.0 |
| Ubuntu 22.04 | 0.12.1 |
| Debian 12 | 0.14.0 |
| Ubuntu 24.04 | 0.16.4 |
| Debian 13 | 0.18.0 |
| current | 0.19.1 |

Minimum: **0.11.0** (pending the maintainer's confirmation; the alternative is 0.14.0; implemented and tested with 0.11.0). 2.0 declared 0.14.0 but actually needed more for some features, found while preparing this plan:

| Feature used by 2.0 | Since | 2.1 behaviour on older restic |
|---|---|---|
| `--option sftp.args=...` (keepalives) | 0.16.1 | build an equivalent `sftp.command` from the `sftp:` URL (user, host, port), with the same `-o` options |
| `check --json` | 0.18.0 | parse the text output of `check` |
| `restore --json` progress and summary | 0.16.0 | no progress; summary computed by ArkHive from the restored tree |
| `init --json` | 0.15.0 | parse the text output of `init` |
| `restore --sparse` | 0.15.0 | already gated in 2.0 |
| `--compression`, repository v2 | 0.14.0 | omit the flag; repository format 1 (no compression); `doctor` and `status` say so |
| exit codes 10 / 11 / 12 | 0.17.0 / 0.17.1 | classified from stderr (already partly in 2.0) |
| `--retry-lock` | 0.16.0 | ArkHive retries itself on "already locked" with backoff |
| full snapshot id in `backup --json` | 0.15.0 | resolve the short id with `snapshots --json` |
| `list locks` without locking | 0.13.0 | always pass `--no-lock` |
| `check --read-data-subset=5%` / `=500M` | 0.12.0 / 0.14.0 | the nearest fraction `n/N`, a different `n` at each run (found by the compat suite) |

Measured on the real binaries while implementing: `backup --json` reports the short snapshot id up to 0.14 and the full one from 0.16 (0.15 not measured; ArkHive resolves any short id, whatever the version); `check` before 0.18 prints pack ids short (8 hex digits) on 0.11 and 0.12; `restore --sparse` is unknown to 0.14.

Design: `ResticVersion` (parsed, comparable) and `ResticCapabilities` (one named boolean per feature above, derived from the version) are domain objects; the restic adapter asks the capabilities instead of comparing version strings inline. A repository with format 2 opened by restic < 0.14 fails with an explanation (`EX_UNAVAILABLE`, hint: install restic >= 0.14).

Tests:

- unit: capabilities per version, argument building per version, text-output parsers with fixtures captured from each version;
- `tests/Compat` (new PHPUnit suite, no Docker): runs the real ArkHive commands (`init`, `backup`, `status`, `ls`, `find`, `restore`, `maintain`, `drill`, `doctor`) against a local repository with the restic binary given in `ARKHIVE_TEST_RESTIC`; plus an SFTP case against a local `sshd` when available;
- CI: a `restic-compat` job runs `tests/Compat` once per version of the table (static release binaries, checksums verified);
- distro matrix: Debian 11 and Debian 12 added, using the distribution's own `restic` package.

## 4. Robustness and resilience

- **Retry policy**: one `RetryPolicy` (attempts, exponential backoff with jitter, deadline) used for transient failures only: repository locked by another client (`--retry-lock` where supported), network errors while opening the repository, SMTP temporary errors (4xx). Never retried: wrong password, missing repository, configuration errors. Every retry is logged with the reason; the final failure keeps the precise classification (75 if still temporary).
  As done: exceptions carry `transient()` (a lock held elsewhere, a timeout, a connection failure); `Application\Resilience\Retrier` runs an operation under a `Domain\Shared\RetryPolicy` and waits through the `Pause` port, which ends at once on SIGINT/SIGTERM. Locks (ArkHive's own and restic's) are waited for up to the new optional key `LOCK_WAIT` (default 300 s, `0` fails at once) around the lock, `backup`, `forget`, `check`, the safety snapshot and `restore`; opening the repository retries connection failures three times (5 s, 15 s); notifications retry 4xx answers and connection failures three times (15 s, 45 s). Deviation: restic's `--retry-lock` is not used. It exists only from 0.16, so ArkHive retries uniformly itself on every supported version, and the wait is logged at each try instead of happening silently inside restic. A refused SSH key or an unknown host key is not retried.
- **Run state**: each `backup`, `maintain` and `drill` records its outcome (start, end, exit code, snapshot id, warnings) atomically (write to temp file, `rename`) in the state directory (`$STATE_DIRECTORY` under systemd, else `/var/lib/arkhive` as root, else `$XDG_STATE_HOME/arkhive`). `status` and `doctor` report the last run of each job and how old the last successful backup is; `status --json` makes it scriptable for monitoring.
  As done: `Domain\Run\RunRecord`/`JobState` (last run and last success per job), the `RunStateStore` port with `Infrastructure\State\JsonRunStateStore` (one 0600 file per job, temp file + `fsync` + `rename`), `Application\Run\RunJournal`. Recording happens in the command's `finished()` hook, before the cleanup, so interruptions (130/143) and every failure are recorded; usage errors (64) are not runs. An unwritable state directory is a warning only. How old the last good backup is comes from the repository itself (`status --max-age`), not from the local record, so a restored host reports the truth.
- **restic cache** in `$CACHE_DIRECTORY` under systemd (so `ProtectSystem` works and the cache survives).
  As done: `Application\System\CacheDirectory` gives restic `RESTIC_CACHE_DIR=$CACHE_DIRECTORY/restic` (first absolute entry) when the unit sets `CacheDirectory=`; a `RESTIC_CACHE_DIR` the operator exported wins, and outside systemd restic keeps its own default.
- **Partial failures**: a failing database dump no longer aborts the others; the backup still runs, the failed dumps are named, the run exits 3 (or 1 if every dump failed and `DUMP_REQUIRED=true`, an optional new key).
  As done: with `DUMP_REQUIRED=true` any failed dump (not only "every dump") fails the run, and with that dump's own exit code (69, 77, 66...) rather than 1, which is what sysexits asks for; the files are still backed up first, since losing them too helps nobody. A full dump filesystem (73, 74) still aborts every dump.
- **Disk full** while staging dumps or restoring is detected and reported as such (74 / 73), with the free space found.
  As done: `Application\System\DiskSpace` adds "(1.20 GiB free in /var/backups, ...)" to a write failure (74) for each local filesystem written: the dump directory for a dump; a local repository, the restic cache and the restore target or the file `restic dump` writes for restic. A file output that fills up (`restic dump` into the import directory) now reports "No space left on device" (74) instead of a bare closed stream. The pre-flight checks (73: not enough space for the dumps, the restore, the dump to import) already named both sizes.
- **Timeouts**: per-process deadlines for dumps and restic calls that should be short (reachability, locks, stats); the long ones (backup, restore, check) are bounded only by the unit's `TimeoutStartSec`, and extended via `EXTEND_TIMEOUT_USEC` while progress is made (step 5).
  As done: `Application\Process\Timeouts` (version 30 s, database metadata query 300 s, restic metadata and init 300 s). restic's reachability, snapshots, locks and stats already had one; added: `restic version`, `restic init`, `pg_dump --version`, and every metadata query of the dumpers and the importer, where a timeout is 75 (transient). Deviation: dumps get no process deadline of their own, since their length grows with the data and a fixed one would kill a healthy large dump; they keep the 10 s connect timeout and are bounded by `TimeoutStartSec`, like backup.
- **Fault-injection e2e** extended with: lock held by another client (retry then 75), SMTP 4xx then success, one database down of two (exit 3, other dump in the snapshot).

## 5. systemd interoperability

- **Notify protocol** (`sd_notify`, implemented in PHP over the `NOTIFY_SOCKET` datagram socket, no libsystemd): `READY=1` once preflight passes, `STATUS=` with the current phase and progress (`systemctl status arkhive-backup` shows "Uploading: 42% of 3.1 GiB"), `EXTEND_TIMEOUT_USEC=` while progress continues, `WATCHDOG=1` when `WatchdogSec` is set, `STOPPING=1` on SIGTERM, `EXIT_STATUS=`/`ERRNO=` before exit. No-op when `NOTIFY_SOCKET` is unset.
  As done: the `ServiceManager` port, `Infrastructure\Systemd\NotifySocket` (udg:// stream, abstract sockets too, `WATCHDOG_PID` honoured) and `Application\Service\ServiceStatus`. The logger turns each step (info, success and error events) into `STATUS=` and each progress report into `STATUS=` "step: progress" (at most every 2 s) with `EXTEND_TIMEOUT_USEC` of 30 minutes; under a service manager restic is asked for progress even when unattended (nothing is drawn). `READY=1` with the first status, `STOPPING=1`, `EXIT_STATUS=` and the outcome at the end; `WATCHDOG=1` with every message and between the reads of a child process and the slices of a wait. `ERRNO=` is not sent: ArkHive's failures are not errno values.
- **Units** (`contrib/systemd`, and `arkhive schedule --systemd`): `Type=notify` with `NotifyAccess=main`; `StateDirectory=arkhive`, `CacheDirectory=arkhive`; `Restart=on-failure` with `RestartSec` and a start limit, and `RestartPreventExitStatus=64 65 66 77 78` so configuration, permission and data errors are not retried; hardening (`ProtectSystem=full`, `ProtectHome=read-only` with the backup paths allowed, `PrivateTmp`, `NoNewPrivileges`, `ProtectKernelTunables`, `ProtectControlGroups`, `RestrictSUIDSGID`, `LockPersonality`); `Nice`, `IOSchedulingClass=idle`, `CPUSchedulingPolicy=batch`; optional `OnFailure=arkhive-failure@%n.service` template that runs `arkhive notify --failed-unit %i` (sends the configured notification with the unit's last journal lines).
  As done: `StateDirectory=arkhive` and `CacheDirectory=arkhive` (a run by hand of the same non-root user finds `/var/lib/arkhive` when it owns it), `ProtectSystem=full`, `ProtectHome=read-only` with `ReadWritePaths=-` for `DUMP_DIRECTORY` and a local repository, `PrivateTmp`, `NoNewPrivileges`, `ProtectKernelTunables`, `ProtectKernelModules`, `ProtectControlGroups`, `RestrictSUIDSGID`, `LockPersonality`, `Nice=10`, `IOSchedulingClass=idle`, `CPUSchedulingPolicy=batch`; verified by `systemd-analyze verify` (`tests/Integration/Schedule/SystemdVerifyTest`, run in CI). Deviations, both for the same reason, that a scheduled job is a run that ends rather than a daemon: (1) `Type=oneshot` with `NotifyAccess=main` instead of `Type=notify`. With `Type=notify` the unit would be "started" at `READY=1`, so `After=` would no longer keep maintain from starting while a backup runs and `systemctl start` would return at once; a oneshot unit still receives `STATUS=`, `EXTEND_TIMEOUT_USEC=` (which extends `TimeoutStartSec`) and `WATCHDOG=1`. (2) No `Restart=`: ArkHive already tries again within the run what may pass on its own (`LOCK_WAIT`, network), each restarted attempt would send its own failure e-mail without knowing whether another attempt follows, and the next timer run comes anyway. With no restart, `RestartPreventExitStatus` has nothing to do.
- **Timers**: `Persistent=true`, `RandomizedDelaySec`, `AccuracySec`; maintain and drill ordered after backup so they never overlap (`Conflicts`/lock).
  As done: `RandomizedDelaySec=10min`, `AccuracySec=1min`, `Persistent=true`; maintain `After=arkhive-backup.service`, drill after both. A maintain started by hand during a backup still waits on the repository lock (`LOCK_WAIT`).
- **`arkhive schedule`**: `--systemd` prints the units; new `--install` writes them to `/etc/systemd/system` only when asked, runs `systemctl daemon-reload` and `enable --now` the timers, and `--status` shows each timer's next and last run and last result (`systemctl show` properties, parsed in PHP).
- **CI**: `systemd-analyze verify` on every generated unit; an e2e job runs the backup unit under a real systemd (container with systemd as PID 1) and asserts `systemctl show -p ExecMainStatus,StatusText` and the journal fields.

## 6. Logging through the journal and syslog

- **journald native protocol**: when `JOURNAL_STREAM` matches stderr (as systemd sets it), or `--log-target journal`, events are sent as datagrams to `/run/systemd/journal/socket` with structured fields: `MESSAGE`, `PRIORITY`, `SYSLOG_IDENTIFIER=arkhive`, `ARKHIVE_COMMAND`, `ARKHIVE_RUN_ID`, `ARKHIVE_SNAPSHOT`, `ARKHIVE_PHASE`, `ARKHIVE_EXIT_STATUS`, and a `MESSAGE_ID` for the key events (backup started, backup finished, backup failed, restore finished, check failed) so they can be filtered with `journalctl MESSAGE_ID=...` and documented in a message catalog (`contrib/systemd/arkhive.catalog`). Falls back to the 2.0 `<N>` prefixed stderr lines if the socket is not writable.
- **syslog** for hosts without systemd (OpenRC, runit, cron): `--log-target syslog` (or `LOG_TARGET=syslog` in the config) uses PHP's `openlog`/`syslog` with facility `LOG_DAEMON` (configurable), ident `arkhive`, the same message text and the structured fields appended as `key=value`.
- `--log-target` values: `auto` (default: journal under systemd, stderr otherwise), `stderr`, `journal`, `syslog`; `--log-file` keeps working alongside any target.
- `doctor` reports the chosen log target and why.
